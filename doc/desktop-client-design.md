# Windows / macOS 桌面客户端设计

状态：0.1.0 桌面预览版已实现，Mac Apple Silicon / Intel 安装包和 Windows Actions 构建已生成。本机 Mac 基础监控完成运行验收；签名相关的 GUI 局域网访问限制见 [desktop-usage.md](desktop-usage.md)。完整本机流量归属仍为后续阶段。

## 目标与推荐方案

使用 Tauri 2 + Vue 3 + Rust 构建桌面客户端。用户安装应用后即可查看本机统计，无需安装 Docker、Python 或 Go。连接已有 NAS 时，使用 NAS 当前的受保护 API。

Rust 负责桌面集成、采集调度、数据存储和网络请求；Vue 负责界面。Tauri 使用系统 WebView，适合复用当前页面。改用纯 Rust GUI 会涉及重写图表、Markdown、表格和设置交互，本项目不优先选择。

| 方案 | 优点 | 主要代价 | 结论 |
| --- | --- | --- | --- |
| Tauri + Vue + Rust 后台 | 复用界面；无需随包携带 Chromium、Python、Go 运行时 | Windows/macOS 采集仍需分别适配 | 推荐 |
| Tauri + Vue + Python/Go 附带进程 | 较多服务逻辑可以沿用 | 打包和进程管理更复杂；Linux 采集逻辑仍无法直接复用 | 仅作为过渡备选 |
| 纯 Rust GUI | 可完全脱离 WebView | 大部分现有界面与交互要重写 | 暂不采用 |

## 当前代码检查结果

- `front-end` 已使用 Vue 3、ECharts 和 Lucide，能复用图表与展示组件。
- `front-end/src/App.vue` 混合了页面、同源 `/api/` 请求和登录跳转。桌面适配需要先抽出数据访问层；容器快捷访问地址也必须从当前 NAS 配置读取，不能继续使用 WebView 的 `location.hostname`。
- `server/main.py` 是 Python/FastAPI 服务，不是可以直接编译成 Rust 的模块。
- `server/go-collector/collector/system.go` 依赖 `/proc/net/dev`、`/proc/net/route`、进程文件和 conntrack。仅切换 Go 编译目标不会提供 Windows/macOS 的统计能力。
- `server/services/system_status.py` 的 GPU、NPU、温度和风扇部分依赖 Linux 设备路径；不能承诺原样移植全部传感器。
- 当前 Mac 已有 Rust、macOS SDK、签名与磁盘映像工具；已安装 Rust 目标为 Apple Silicon。完整 Windows 构建与运行尚未验证。
- 只读运行本机 `nettop -L 1 -n -x -J bytes_in,bytes_out` 成功取得 CSV 数据。这个结果只证明当前机器存在可用采集路径，不代表所有 macOS 版本和权限条件都已通过验证。

## 双模式交互

应用顶部常驻数据来源选择：本机、已保存的 NAS。允许保存多个 NAS；默认只订阅当前选中的目标。

本机模式显示网卡、进程、连接、历史和系统资源；NAS 模式沿用远端的统计、Docker、监控、通知与 AI 功能。切换目标时取消旧请求、清理实时图表窗口，禁止不同机器的数据混入同一视图。

登录、规则修改和容器操作始终归属当前目标。操作确认页显示目标名称；远端会话失效后重新登录，不能切换为匿名请求。远端数据不自动复制到本地历史库。

桌面功能包括系统托盘、关闭窗口后继续监控、明确的“退出并停止本机监控”、开机启动选项、数据目录和日志目录入口。开机启动默认关闭；系统睡眠期间不制造零值采样或补算不存在的流量。

## 模块边界

按既有目录约定组织，保持 MVC 及平台适配边界：

```text
doc/
  desktop-client-design.md
front-end/
  src/api/                  # 浏览器 HTTP / 桌面 IPC 数据访问适配
  src/views/                # 按页面逐步抽离现有 App.vue
  src/components/           # 共用图表、列表、设置组件
server/
  desktop/                  # Rust workspace 与 Tauri 配置
    app/                    # 桌面入口、托盘、生命周期
    core/src/               # 首版以模块划分，避免过早拆分多个 crate
      metrics.rs            # 数据模型与计数器差值
      monitor.rs            # Windows / macOS 基础采样调度
      storage.rs            # SQLite 历史、配置与连接资料
      nas.rs                # 远端 API、独立会话、流式响应
```

控制器只校验参数并调用业务服务；存储模块负责查询和事务；视图不直接执行 SQL、系统命令或调用驱动。现有 NAS Python/Go 服务继续独立构建，桌面首版不要求改写 NAS 后端。

本机 UI 通过受限 Tauri IPC 调用 Rust，不新增面向局域网的监听端口。Rust 向前端提供与现有页面接近的结构，但明确附带平台能力和采集质量信息。

## 本机采集

| 能力 | Windows 路径 | macOS 路径 | 验收要求 |
| --- | --- | --- | --- |
| 网卡总收发、CPU、内存、进程资源 | Windows 系统 API / 成熟 Rust 库 | 系统 API / 成熟 Rust 库 | 与系统工具对比；计数重置不产生负速率 |
| TCP/UDP 端点、进程归属 | IP Helper 的连接与 PID 信息 | 系统连接信息与 nettop 采集记录 | 区分监听端口和活动连接；未知 PID 明确标注 |
| 进程收发、公网/内网分类 | 优先验证 ETW 网络事件，并结合连接表 | 优先验证常驻 nettop CSV 采集进程及连接记录 | 不能用进程总流量推断公网占比 |
| GPU、温度、风扇 | 按显卡及传感器接口适配 | 按机型及系统接口适配 | 没有数据时显示“不支持/需要权限”，不显示虚构的零 |

优先采用系统已有设施。ETW 的权限、事件字段、丢失事件与不同 Windows 版本行为需要实机验证；macOS 的 nettop 输出和进程可见性也需要版本、权限及异常退出测试。若需要附加驱动或系统扩展，单独评估分发与授权，不静默安装。

公网分类根据远端地址进行，并排除私网、回环、链路本地、多播等非公网地址。VPN、代理、隧道和虚拟网卡可能只能观察到外层连接；不能将该流量伪装成已确定归属的原始应用流量。

网卡字节计数、连接字节计数和进程字节计数可能来自不同层级，页面保留来源与覆盖范围，不强制补齐差额。连接数表示当前可观察的活动公网连接，不累计历史连接条目，也不把 UDP 监听端口当成一个公网连接。

## 权限与数据

- 主界面保持普通用户权限；需要更高权限的采集能力由独立小服务提供。服务接口只允许固定的采集操作，不暴露任意命令执行。
- 本机基础功能可在普通用户权限下启动。缺少高级采集权限时明确显示能力状态，并提供按需启用入口。
- NAS 密码和 AI 密钥使用 macOS Keychain / Windows Credential Manager；SQLite 保存配置、规则与历史，不保存明文凭据。每个 NAS 会话独立。
- NAS HTTP 请求由 Rust 发起，目标限定为用户配置的服务地址。默认验证 HTTPS 证书；兼容用户明确配置的局域网 HTTP，不把认证信息带往跨域重定向。
- WebView 加载随应用发布的前端资源；外部链接交给系统浏览器。远端页面和 AI Markdown 不获得本机高权限 IPC 能力。
- 本机 SQLite 使用应用数据目录，单写入队列、批量事务和 WAL；日志滚动存储。配置、历史、告警证据分别提供维护入口，不通过删整个数据库清历史。
- Rust 数据库与 NAS 数据库分开维护。桌面安装、卸载和目标切换不修改 NAS 的数据库或挂载目录。

## 性能原则

默认实时刷新约 1 秒；尽可能采用事件或累计计数差值。macOS 的命令采集适配使用一个可管理的常驻进程，不每秒新建一个 shell。

所有页面共用采集结果；关闭窗口后暂停图表渲染与界面订阅，用户启用的后台采集、落库和规则判断继续工作。连接详情分页按需读取；进程与连接缓存按时间和数量设上限，超限时记录覆盖率变化。

网络与数据库工作不阻塞 UI。历史按时间桶聚合，告警保存触发原因与当时可归属的进程、连接摘要。AI 仅在请求分析时调用，并继续使用配置变更预览及确认机制。

Tauri 能减少随应用打包的浏览器运行时，但不预设实际 RSS 或 CPU 数值。安装包体积、采集服务和 WebView 总资源占用都以测量结果为准。

## 交付顺序

1. **桌面基础与平台验证**：建立 Rust/Tauri 工程，抽离数据访问层，完成本机/NAS 切换、基础资源统计、托盘及本地 SQLite；分别验证 macOS 网络采集和 Windows ETW 可行性。
2. **完整流量监控**：网卡、公网/内网、进程、连接、历史、告警证据及后台运行。高级采集未通过验收的平台应标记为预览版，不以“安装包能打开”代替监控功能验收。
3. **功能扩展**：本机 AI 分析及配置助手、额外传感器与可选 Docker 引擎适配。NAS 模式继续访问远端已具备的这些能力。

首个可测试安装包定位为桌面预览版，提供本机基础监控与 NAS 连接；完整桌面版须完成第 2 阶段。系统级限速、任意本机进程自动结束/重启、VPN 内层归属及所有硬件传感器不作为首版承诺。既有 NAS 容器保护通过远端服务执行。

## 构建与验证

- Windows 首先提供 x64 安装程序；macOS 提供 Apple Silicon 与 Intel 构建。Windows ARM64 不默认纳入首批。
- 使用独立桌面版本和发布标签；保留现有 NAS `VERSION` 与 Docker `latest` 发布流程，避免仅改桌面却触发 NAS 发版。
- macOS 先在当前 Mac 构建、运行；Windows 使用 Windows 构建机或 GitHub Actions 原生构建。编译成功与真实 Windows 运行验收分别报告。
- 面向公开分发的签名、公证与证书配置单独完成。没有发布证书时明确标识未签名测试包，不声称已通过平台公证或可信发布。
- 回归测试覆盖采样差值、地址分类、PID 重用、连接过期、系统休眠恢复、配置持久化、NAS 认证隔离、目标切换取消请求和后台任务停止。
- 两个平台分别对比系统工具，验证 HTTP 下载/上传、LAN 传输、IPv6、VPN 场景与空闲负载；进行长时间缓存及内存增长观察。
